# Filament — technical reference

The deep reference for the Filament light client. For a one-page introduction and build and run
instructions, read the repository `README.md` first.

> **Source of truth.** This file lives next to the code (`crates/filament/src/mmr_client/`) and is
> checked against it. The public repository publishes it as `docs/reference.md`. It was rewritten on
> Nov 5, 2026: the earlier text predated the thin sync, the 148-byte beacon header, the derived
> genesis and the crate split, and described types that no longer exist. Statements below were taken
> from the code and from the shared consensus vectors; where something was not checked, it says so.

---

## 1. What Filament is

Filament follows the chains of the Heaviest Chain Rule Network (HCRN) **without trusting a single node and without storing
the chains**. Per chain it keeps the Merkle Mountain Range (MMR) **peaks**, the leaf count and the
last 16 headers: a few kilobytes, independent of chain length. Full nodes (**Keystone**) serve the
data; Filament checks it.

What it checks, in order:

1. **Genesis.** Block 0 is generated locally from a genesis config (a preset, or the genesis file the
   nodes load) by the same generator the nodes use. Nothing about block 0 comes from a peer.
2. **Proof of work** of every header it accepts.
3. **Linkage.** Each header's `prev_mmr_root` must equal the root Filament computed itself, and each
   new leaf must produce the `current_mmr_root` the header claims.
4. **Chain weight**, computed locally from the leaves' rBits. A peer's claimed weight is never used.
5. **Agreement of several Keystones** (a quorum of `required_keystones()`: 2, or 1 with
   `--allow-single-keystone`), so one node cannot hide a heavier chain.
6. For payments: an **output-in-block proof** against the block's `tx_merkle_root`.

What it does **not** do: validate transactions (signatures, unspent inputs), run the consensus
rules, mine, or hold a UTXO set. It trusts the network's proof of work, like every light client
(§11).

In the node's repository the types crate is called `network-common`. The public repository maps
that name to `filament-types`, so source written as `network_common::common::…` compiles in both.

`tests/vectors/consensus_v1.json`**, a file generated by the node and run by both repositories (§12).

## 3. Data model

### WeightedHash

A 32-byte MMR value: 28 bytes of hash and a 32-bit **rBits** field (a compact difficulty).

| | hash (bytes 0–27) | rBits (bytes 28–31) |
|---|---|---|
| leaf | first 28 bytes of the block's PoW hash (`SHA256d`), not re-hashed | the header's `bits` (shard: `difficulty`) |
| internal node | `BLAKE3` of the children, truncated | `rbits_add(left, right)` |

The root's rBits is the chain's cumulative work, so weight is read from the root and never carried
separately. Peaks are bagged right to left into the root (`bag_peaks_weighted_u128`).

### Positional addressing

An output is identified by `(height, output_index)`, never by a transaction hash. The MMR is a flat
vector, and where a node lives is arithmetic on the leaf count (`mmr_math`: `peak_descriptors`,
`replay_peaks_after_appends`, `fork_path_positions`), so Filament never builds or searches a tree.

### Headers and records

| Type | Size | Content |
|---|---|---|
| `WireBeaconHeader` | 148 B | version, `prev_mmr_root`, delta, bits, nonce, height, `tx_merkle_root`, `merged_mining_root`, `coinbase_hash`. Enough to check the PoW on its own. |
| `FullShardBlockData` | ~0.3–2.2 KB | A shard block record: height, MMR roots, `tx_merkle_root`, `difficulty`, the **auxiliary beacon header** the block was merge-mined with, and its **merged-mining sibling path**. A shard block has no PoW of its own; its work is the aux header's. |

The number of active chains is **not a separate header field**. It is the 12 low bits of
`merged_mining_root` (the last two bytes also carry the tree height), so the PoW commitment covers
it (`MergedMiningHash::chain_count_of_root`).

### Proofs (`filament-types::proofs`)

| Proof | Use |
|---|---|
| `WeightedMMRRangeProof` | A run of consecutive leaves against a root. Used by thin sync. |
| `WeightedMMRBatchProof` | Scattered leaves against a root. |
| `ForkProof`, `WeightedChainWeightProof` | Compare two chains, and carry weight evidence. |
| `TxInclusionProof` | The transaction slices that own an output, plus the merkle path to `tx_merkle_root`. |

All verify against an **anchor**, the genesis Bitcoin anchor hash. A wrong network shows up as
`Invalid chain summary proof`.

### The shard block check

`verify_shard_id_and_mmn` ties four things together. The aux header's PoW hash meets the shard
target. Its last `s` bits route it to this shard (value `v` selects shard `v − 1`; 0 is the beacon).
The shard's leaf sits in the aux `merged_mining_root` by the sibling path. And the chain count in
that root is in the admissible range.

## 4. Thin sync

Thin sync is the sync that follows chains with the smallest traffic. It is enabled with
`--thin-sync` and is **off by default until a fleet run**. Design and measurements:
`Filament_Thin_Sync_Design.md` in the node's repository.

Per chain and per Keystone, each tick:

1. `GET /chain/tip` returns height, leaf count and root (~110 B).
2. If nothing changed, nothing else happens. If the Keystone is ahead by a few blocks, Filament calls
   `GET /chain/headers/{from}?max=N` (up to 64 headers). Otherwise, or after any failed check, it
   calls `GET /chain/session?headers=16`: the newest 16 headers and one range proof.
3. Every header is checked as in §1. A session that fails verification marks that Keystone `rejected`.
4. A state is trusted only when at least `required_keystones()` distinct Keystones **contain** it
   (same root at the same leaf count, or ahead and holding the next header). The heaviest supported
   state wins.

Shards (`--thin-shard N`, plus the shard of every open invoice) use the same loop over
`/shard/{id}/chain/{tip,session,headers}`. A shard's anchor and genesis difficulty are derived from
beacon headers Filament verified itself (`/chain/header-proof/{from}`), never from a Keystone's
word. Only shards listed in the genesis (`initial_shard_count`) are followed this way. A shard
opened later by an expand vote cannot be verified yet and is confirmed at lower assurance (below).

Measured on small test chains (JSON bytes): tip poll 109 B; session 7.5 KB (beacon) or 10–12 KB
(shard); one new beacon block 346 B. The older full `/chain/summary` was 134–159 KB.

### Invoice confirmation

An invoice becomes `Confirmed` only when the shard's thin state is `synced`, the paying block is at
least `confirmation_depth` (default 6) below Filament's own verified tip, and the paying **output**
is proved inside that block (`bind_payment`). The invoice carries an `assurance` field:

| `assurance` | Meaning |
|---|---|
| `verified_chain` | The payment was proved inside a block of a shard chain Filament verified itself. Strongest. |
| `keystone_quorum` | Dynamic shard: depth from a Keystone tip quorum, payment proved by a quorum of Keystones. |
| `keystone_tip` | Thin sync off: depth from Keystone-reported tips, no payment proof. Weakest. |

## 5. Networks and genesis

Genesis facts are **derived**, not stored. `BeaconGenesisConfig` presets give every field.
`GenesisGenerator::generate_beacon_genesis` builds block 0 (coinbase with the premine, merkle root,
v3 header hash), and `genesis_mmr_root` gives the first root. The vectors compare the hash for every
preset and for the checked-in genesis files.

| Network | Chains at genesis | Start difficulty | Target ceiling | Note |
|---|---|---|---|---|
| `mainnet` | 3 | 128 | 2^212 | ASIC |
| `testnet1` | 3 | 128 | 2^240 | CPU, historical |
| `testnet2` | 15 (s = 4) | 512 | 2^240 | CPU, the announced community network |
| `testnet3` | 3 | 128 | 2^216 | ASIC |
| `devnet` | 3 | 128 | 2^240 | Local. The name does not identify one chain: any soak genesis runs as `devnet`. |
| `testnet-stress` | 3 | 128 | 2^240 | Epochs of 256 blocks; genesis hash pinned in the preset. |

For anything but a stock preset, pass the genesis file (`--genesis-file`, or `--genesis`):
`MultiChainClient::init_from_genesis_file`. A file that does not load stops startup.

`light_client_config.toml` and `examples/light_client_config.example.toml` hold the same facts as a
bootstrap config. The test `bootstrap_config_matches_presets` fails if they drift from the presets.
Hashes are in internal byte order, the reverse of a block explorer's display.

## 6. Using the library

```rust
use filament::{InMemoryStorage, MultiChainClient};
use filament::mmr_client::multi_chain_client::PeerChainSummaryResponse;

// Block 0 from a preset's table in the bootstrap config…
let mut client = MultiChainClient::from_config_file("light_client_config.toml", Box::new(InMemoryStorage::new()))?;
client.init_from_network("testnet2").await?;
// …or from the genesis file the nodes load:
// client.init_from_genesis_file(std::path::Path::new("genesis_testnet2.toml")).await?;

// Fetch /chain/summary from a Keystone yourself and hand it over. Proofs are checked against the anchor.
let outcome = client
    .reconcile_beacon_summaries(vec![PeerChainSummaryResponse { peer_id, summary }])
    .await?;
let tip = client.get_beacon_state().await?.tip.height();
```

`examples/quickstart.rs` is the compiled version of this snippet. The thin sync loop and the HTTP
server do the fetching for you; the library on its own has no transport.

Other entry points: `add_shard_chain`, `get_shard_state`, `watch_address` and the `handle_tx_*_notif`
handlers (Path-2), `get_trusted_sync_status`, `report_beacon_disagreement`.

**Verification strategy.** `VerificationStrategy` (`Full` by default, `Light`, `Paranoid`) applies to
chain-weight verification (`verify_chain_weight_proof_with_strategy`). Batch and range proofs verify
through `WeightedMMR*Proof::verify_with_anchor`.

**Parallel verification.** `verify_batch_proofs_parallel` and `verify_range_proofs_parallel` use a
rayon pool created once. Parallelism starts at 64 batch proofs or 16 range proofs and uses at most
`min(cores / 2, 4)` threads (`PROOF_PARALLEL_THRESHOLD_BATCH`, `PROOF_PARALLEL_THRESHOLD_RANGE`,
`PROOF_MAX_THREADS`).

## 7. The `filament` binary

```bash
cargo build --release -p filament --features full-node --bin filament
```

| Flag | Meaning |
|---|---|
| `--network` | `mainnet`, `testnet1`, `testnet2`, `testnet3`, `devnet`, `testnet-stress` |
| `--genesis-file PATH` (`--genesis`) | The genesis file the nodes load. Required for anything but a preset. |
| `--keystone URL`, `--keystone-extra URL` (repeatable) | Keystone REST endpoints. Wallet operations fan out to all of them. |
| `--keystone-summary-port N` | Port of the light-client API on each Keystone host (default 8080) |
| `--keystone-p2p-port N` | node P2P port on each Keystone host (default 18334; 0 skips the dial) |
| `--manual-peer HOST:PORT` (repeatable) | An explicit P2P peer |
| `--disable-p2p`, `--p2p-listen HOST:PORT` | Path-2 P2P off, or the listen address |
| `--thin-sync`, `--thin-shard N` (repeatable) | Thin sync for the beacon, and for shard N |
| `--allow-single-keystone` | Accept a quorum of one |
| `--confirmation-depth N` | Depth before an invoice confirms (default 6) |
| `--indexer URL` (repeatable) | Eratosthenes endpoints, used by the escrow funding watch |
| `--address HEX`, `--signing-key-file`, `--data-dir`, `--port` | Wallet address and key, data directory, API port (default 7380) |

Settings persist in the data directory, and flags override only what they set.

**HTTP API** on `127.0.0.1:7380` (loopback only). Groups: `/health`;
`/sync/{status,trust,proof-latency}`; `/chain/{all,beacon,shard/{id}}`; `/peers`; `/proofs/verify`;
`/events` (SSE); `/config`, `/logs`, `/notifications`;
`/wallet/{address,balance,utxos,history,fee,send,sign,sign-message,broadcast}`;
`/invoice/{create,list,parse,{id},{id}/cancel,{id}/hints}`; `/contacts`; `/escrow/…`;
`/f2f/{pubkey,messages,send}`. The wallet routes are experimental on testnet. Keep a Keystone's
wallet port off the public internet.

**Beacon coins and several accounts.** One address holds shard coins and beacon coins; the wallet tracks both
(`beacon_confirmed` / `beacon_unconfirmed` in `/wallet/balance`). `/wallet/send`, `/wallet/sign` and
`/wallet/broadcast` take `"beacon": true` to spend beacon coins: the transaction is signed for chain id 0 and
posted to the Keystone's `/mempool/submit/beacon`. Besides the account the process starts with (`main`), the client
can hold more accounts, each with its own address and key (encrypted with its own password) or watch-only:
`/accounts` (list, create), `/accounts/{import,watch}`, `/accounts/{id}/{unlock,lock,rename,backup}`,
`DELETE /accounts/{id}?confirm=yes`; the wallet routes take `?account=<id>`. Like the rest of the wallet routes,
these are experimental on testnet.

## 8. Keystone endpoints Filament calls

| Route | Use |
|---|---|
| `GET /chain/tip`, `/chain/session`, `/chain/headers/{from}`, `/chain/header-proof/{from}` | Beacon thin sync |
| `GET /shard/{id}/chain/{tip,session,headers/{from}}` | Shard thin sync |
| `GET /chain/range/{a}/{b}`, `/shard/{id}/chain/range/{a}/{b}` | Range proof, to bind an older block |
| `GET /shard/{id}/tx-proof?height=&output_idx=` | Output-in-block proof |
| `GET /chain/summary` | The older summary poll (thin sync off) |
| `POST /mempool/submit?shard=N` | Submit a signed transaction |

## 9. Path-2 P2P

`filament-p2p` speaks the node P2P wire protocol **v17** and negotiates `min(ours, theirs)`. A Keystone pushes
`TxInclusionNotif`, `TxSpentNotif` and `TxRevertNotif` for the addresses Filament watches
(`WatchAddress`). Identity is checked at the handshake: first the 4-byte network magic (for example
`SHTS` for testnet-stress, `SHT2` for testnet2), then the genesis hash. When both sides send a
non-zero hash and the hashes differ, the connection is refused. The client **derives** its hash from
the network's preset; `devnet` sends zero (unpinned). A peer that never sends `version` or `verack`
is dropped after 5 s, and a dial that does not connect within 10 s is abandoned.

Probe a node: `scripts/p2p_handshake_probe.sh HOST:18334 testnet2`.

## 10. Storage and the rest of the product

* **Storage.** `LightClientStorage` with `InMemoryStorage` and `FileStorage`. Keys are namespaced by
  chain (`ChainId::Beacon`, `ChainId::Shard(n)`).
* **Wallet.** Watch-only by default (UTXO discovery is delegated and checked against the local MMR).
  An optional encrypted hot key (`hot_key.json`) signs locally.
* **Invoices and F2F.** Receiver-initiated payment requests (`shisha:` URIs, a binary codec and a state
  machine: Created, Shared, PaymentSent, Pending, Confirmed, with Expired, Archived and
  ReorgReverted), and encrypted Filament-to-Filament messages (ECDH, BLAKE3 KDF, ChaCha20-Poly1305),
  relayed through Keystones.
* **Escrow.** Policy-hash outputs and their wallet obligations (spec in the node's repository:
  `Escrow_Policy_Hash_Consensus_Spec.md`).
* **Address book.** Local contacts with QR export.

## 11. Security model

* **No zero-knowledge proofs, and none will be.** Every proof is a hash-based inclusion or weight proof.
  A ZK "proof" is a probabilistic argument, not an absolute proof; its security rests on assumptions
  pushed beyond the domain they were established for, and a trusted setup defeats "trustless" by
  definition. In a trustless setting only mathematics is trusted. Fork choice must be checkable from
  independent peers. This is a design position, not an omission, and it needs no outside sign-off.
  The full argument is in the repository README.
* **Trust assumptions.** The genesis config is correct (it is derived locally, so a wrong preset is a
  build-time bug the vectors catch). At least one of the Keystones you query is honest; with a quorum
  of two, a single liar is outvoted. The network's proof-of-work and hash assumptions hold.
* **Stated limits.**
  * The work check covers the work a header *claims*, not that it equals the difficulty adjustment's
    expected value. Comparing Keystones is what rejects a cheap fake chain.
  * A shard header's chain count is the miner's claim. It is checked against its own sibling path but
    not against the beacon's admissible range for that epoch.
  * A proved output is in a block. That the transaction is *valid* rests on the chain's proof of work.
  * Dynamic (expand-vote) shards are not verified by thin sync (§4).
  * Thin sync has not run against a live fleet yet.

## 12. Testing and provenance

* `cargo test --workspace --features full-node` runs the unit tests and the shared vectors.
* `crates/filament-types/tests/consensus_vectors.rs` runs `tests/vectors/consensus_v1.json`: SHA256d,
  `hash_pair`, the weighted-hash functions, MMR peak maths, hash sorting, sighash and txid, the
  148-byte header, PoW targets, the chain-count range, genesis (six presets, four genesis files and the
  genesis hash), shard body leaves and proofs, shard headers, the merged-mining check, and the
  bincode and JSON wire formats of every thin-sync response. **Never edit the file by hand.** A failing
  case means the public code drifted from the node.
* `scripts/sync_filament_public.sh` copies `crates/filament` from the node's repository and keeps one
  overlay, `filament_p2p.rs`. `VERSION` records the commit it was synced from.
